# Blackbook

Vara5's internal Client 360 platform for a luxury travel agency. Deployed at
blackbook.vara5.travel. Read `README.md` first;
the source requirements live in `docs/`.

## Non-negotiables

- **Components never touch the database.** Every write goes through a service in
  `src/services/`, which asserts a capability, validates with Zod, runs in a
  transaction and writes an audit row.
- **Services are `server-only`.** Shared constants, labels and Zod schemas that
  a client component needs belong in `src/domain/`, which must stay free of
  database imports.
- **Authorization lives in the service layer**, not in the proxy and not in the
  UI. Hiding a button is presentation; `requireCapability` is the boundary.
- **`activity_log` is append-only**, enforced by a database trigger. Do not add
  code that updates or deletes it. The single permitted update is a
  foreign-key SET NULL clearing a client or household reference during erasure.
- **Soft delete by default.** Set `archivedAt`; do not hard-delete client data
  except to honour an erasure request.
- **Preference vocabulary is data, not code.** New destinations, hotels and
  airlines are rows in `preference_option`, added at runtime. Only add an enum
  when a field genuinely has one fixed answer.

## Brand

- Colours come from the brand guide, not from taste. `--brand-*` in
  `src/app/globals.css` holds the five production values; every other token is
  derived from them. Components use semantic tokens, never `--brand-*` directly.
- Champagne is the accent and is deliberately sparse. Ink carries primary
  actions on light surfaces, champagne on dark ones.
- The logo is `Image` tags pointing at `public/brand`, not a component. Where it
  follows the theme, render the ink and champagne files together and let
  `dark:hidden` / `hidden dark:block` choose, so it is right before hydration.
- **Never paint a fixed brand panel with `--primary`.** It inverts between
  themes. Use `--brand-surface`, which is black with the champagne mark in both.

## Conventions

- Migrations are generated by drizzle-kit (`pnpm db:generate`) and applied by
  drizzle-orm's migrator (`pnpm db:migrate`), which is plain JavaScript with no
  build step so the same command runs inside the production image. Do not
  reintroduce drizzle-kit as a runtime dependency.
  Hand-written SQL goes in a `--custom` migration so the journal stays correct.
- The generated `search_document` column on `customer` is intentionally absent
  from the Drizzle schema; reference it through raw `sql` in the repository.
- **Do not put a correlated subquery in a Drizzle select list on a single-table
  query.** Drizzle omits the table prefix in the select list when there are no
  joins, so an outer column reference renders bare and silently binds to the
  subquery's own table instead. It fails quietly, with a plausible wrong answer
  rather than an error. Use a join with `alias()` and `groupBy`, or put the
  subquery in the WHERE clause, where Drizzle does qualify.
- British English in user-facing copy. Dates render as `12 Oct 2026`.
- Run `pnpm typecheck`, `pnpm lint` and `pnpm test` before calling work done.
- Tests hit a real throwaway Postgres database, not a mock, because much of the
  behaviour is in the schema. Only `src/auth/current-actor.ts` is stubbed, so
  authorization is always exercised for real. Add a case to the file matching
  the requirements section it belongs to.
- **Partial updates must only write the fields the caller sent.** Several
  schemas use `.optional().transform(v => v ?? null)`, which turns an omitted
  field into null; writing the whole parsed object would blank everything the
  form did not include. Use `onlyProvided` from `src/domain/shared.ts`.
- **Do not interpolate a JS `Date` into a raw `sql` expression inside `.set()`.**
  Drizzle applies the column's type hint and the driver cannot bind it. Pass an
  ISO string with an explicit `::timestamptz` cast.
- AI goes through OpenRouter behind `src/ai/model.ts`. One key, any model, set
  by `AI_MODEL`. Do not add a second provider SDK or a second key.
- The deployment has no host shell. Anything that must run once either happens
  in `src/instrumentation.ts`, which must be idempotent and must never take the
  server down, or is reachable through the UI.
- **Every table in `public` has row-level security enabled with no policies.**
  Not for the app's own authorization, which lives in the service layer, but to
  shut PostgREST out: Blackbook shares a database with a Supabase stack, and
  anything readable in `public` is reachable over HTTP with the anon key. The
  app connects as the table owner, which bypasses RLS, so this is invisible to
  it. **A new table needs the same treatment in its migration.**
- **The container health check must never touch the database.** Swarm kills and
  reschedules unhealthy tasks, so a database-dependent probe becomes a restart
  loop that serves 502s and hides the cause. Liveness is `/api/health/live` and
  checks nothing; readiness is `/api/health`.
- Shell scripts are LF via `.gitattributes`. A CRLF shebang makes the kernel
  look for `/bin/sh
` and fail with a message that names the file, not the
  ending.
- **Do not turn session cookie caching back on.** It caches the role, so a
  demoted or suspended user keeps their access until it expires.
- **Accounts cannot be created with SQL.** Better Auth owns password hashing, so
  every account is made in-process: `/setup` for the first administrator, Team
  for everyone after. `/setup` is open only while no account exists.
- **Supabase's API is not a substitute for the connection string.** The service
  key and URL reach PostgREST; this application needs SQL, for transactions,
  migrations, `tsvector` ranking and trigram search. Do not add `supabase-js`.
- **`DEV_DATABASE_URL` is local, `DATABASE_URL` is live.** Nothing falls back
  between them. Local commands use the first; only `db:*:prod` uses the second.
  The test suite and the seed refuse any non-local host.
- **Nothing may read the database at import time.** `next build` loads every
  route module with no environment, so the client in `src/db/index.ts` is built
  lazily on first use. Keep it that way.
- **Escape tsquery operators, never strip them.** Stripping breaks names with
  apostrophes and hyphens, which are common in a client list, and it fails
  silently with a plausible wrong answer. Control characters are removed at the
  search input boundary in `clientSearchSchema`, not in a query builder.
- **Archiving and erasing are different capabilities.** `client.archive` is
  reversible and available to managers. `client.destroy` is administrator-only,
  requires the record to be archived already and a written reason, and writes
  its audit entry before the delete.
- Two records, two purposes. `activity_log` is the business audit trail and is
  append-only. `src/lib/logger.ts` is operational telemetry to stdout, and it
  redacts personal data by field name. Never log client values, only ids.
